# 便签独立 Markdown 文件存储开发方案

日期：2026-10-25。状态：待实施。本文定义便签从汇总 JSON 迁移到独立文件的开发范围、数据约定、保存流程和验收要求，不代表功能已经完成。

## 1. 目标与范围

每张便签对应一个独立的 `.md` 文件，文件包含正文与恢复该便签所需的业务元数据。快捷窗口与桌面入口继续访问同一张便签、共享同一个编辑会话。修改一张便签时，只保存当前便签并更新受影响的视图，保存成本不再随全部便签正文的总量增长。

本次同时解决安全迁移、连续输入保存、失败后草稿保留、删除撤销、附件路径和备份恢复兼容。保留现有原生 Markdown 编辑器与 UI，不新增数据库、第三方解析库、逐字符写入日志或通用存储框架。

近期剪贴板历史和非便签随记继续使用 JSON。待办事项的备注不在本次拆分范围。外部编辑器实时双向同步、任意文件重命名跟踪和多人协作不作为本次交付前提；正常外部编辑的重新读取和覆盖冲突检测见第 8 节。

## 2. 当前实现与需要消除的开销

`QuickCaptureStore` 当前将 `QuickCaptureStoreData` 整体保存到 `data/quick-capture/quick-capture.json`。其中包含便签、非便签记录、近期剪贴板记录以及快捷标签关闭历史。新建便签默认是 Markdown，但正文仍在 JSON 的 `Body` 字段内。

`NoteEditingSession` 通过 `PatchNoteAsync` 更新有改动的字段，最终由 `QuickCaptureService.SaveCoreAsync` 调用全量存储。当前自动保存采用约 600 毫秒防抖，`MarkdownEditingSession` 已有修订跟踪、保存互斥和完成编辑时的补存循环，可继续复用。

保存后还有全局处理：每个便签会话收到 `QuickCaptureService.Changed` 后，会通过 `GetDataAsync` 取得整个集合的对象副本，再查找自己的记录；便签列表会重新筛选、排序和同步。正文字符串本身未必被复制，但集合遍历、记录与附件对象分配及界面更新仍然存在。

因此，本次不能只改变文件扩展名或把全量保存循环改成逐个写文件。正常编辑必须退出全量存储、全量取数和全量刷新路径。

## 3. 文件布局与数据归属

以下路径相对于当前数据根目录，不改变生产版与开发版的数据目录解析规则：

```text
data/quick-capture/
  quick-capture.json                  剪贴板、非便签记录、视图状态及格式切换标记
  notes/
    <note-id>.md                      当前便签文件，包括必要元数据
    <note-id>.md.bak                  当前文件的上一版恢复副本
  attachments/<note-id>/             现有托管附件目录
  images/                            现有图片存储，迁移时不强制重排
  thumbnails/                        可重建缩略图
  exports/                           临时导出文件
```

便签 ID 稳定，修改标题不重命名文件。新 ID 沿用现有生成规则；旧 ID 原样保留。构造路径必须验证 ID 是合法的单个文件名片段，禁止分隔符、上级目录跳转和保留名称。遇到不能直接映射的历史 ID，使用可逆的安全文件名编码，不能擅自更换业务 ID。

### 3.1 单个便签文件

采用 UTF-8 无 BOM 写出，读取兼容 UTF-8 BOM。文件首部使用带固定标记的 HTML 注释保存 JSON 元数据，其后为原始正文。这样可以复用 `System.Text.Json`，并让正文与元数据在一次文件提交中更新，无须新增 YAML 解析依赖或协调正文与旁置元数据两个文件的提交。

示例中的时间、ID 和附件仅用于说明格式：

```markdown
<!-- winsticker-note
{
  "version": 1,
  "id": "739530025dc24e37983ec328fbff9d142",
  "title": "项目记录",
  "contentFormat": "Markdown",
  "createdAt": "2026-10-25T12:00:00+08:00",
  "updatedAt": "2026-10-25T12:10:00+08:00",
  "appearancePreset": "StickyYellow",
  "isPinned": false,
  "sortOrder": 0,
  "pinnedSortOrder": -1,
  "tags": [],
  "isDeleted": false,
  "attachments": []
}
-->
# 今天的安排

- [ ] 整理需求
```

这是一项 WinSticker 文件格式扩展，不声称其他编辑器会识别这些元数据为自己的文档属性。用户可以直接读取、编辑后面的 Markdown 正文。应用编辑器只接收解码后的正文，不显示内部头部。

头部识别只发生在文件开头，不能把正文中相同的注释当成元数据。JSON 使用默认安全转义，防止标题或其他字符串中的 `-->` 提前结束注释；不得启用不安全的宽松转义。解码器应明确记录头部边界，只移除头部及约定的一个分隔换行，保留正文的空白、换行、代码块和空正文。读取使用严格 UTF-8 解码，非法字节应进入单文件错误处理，不能静默替换字符后覆盖源文件。未知元数据字段读取后必须保留；高于当前支持版本的文件进入只读错误状态，不能按旧版本重写。

完整字段归属如下，示例只展示其中一部分：

| 当前字段 | 新格式中的处理 |
| --- | --- |
| `Body` | 仅保存到头部之后的正文，不进入元数据 JSON |
| `Id`、`Title`、`ContentFormat`、`CreatedAt`、`UpdatedAt` | 保存到单文件元数据，保持原值及空值语义 |
| `Type`、`Url`、`ImagePath`、`ContentHash`、`SourceKind`、`Tags`、`DeviceId` | 保存到单文件元数据，兼容原分类、去重、来源及同步字段 |
| `AppearancePreset`、`IsPinned`、`SortOrder`、`PinnedSortOrder` | 保存到单文件元数据，沿用现有外观、收藏与文档排序语义 |
| `Attachments` | 保存完整附件记录，按第 3.3 节处理路径 |
| `IsNote`、`IsRecent` | 对有效独立便签恢复为 `true`、`false`；旧删除记录的分类信息须足以保留正确的删除保护 |
| `IsDeleted`、`ArchivedAt` | 保留删除状态与必要历史值；快捷标签关闭历史仍以独立宿主状态为准 |

实现时逐项对照 `QuickCaptureItem`，字段新增后更新映射，不能只保存示例中的字段。元数据序列化继续使用适用于现有 Native AOT 构建的源生成上下文，未知字段保留也不得依赖运行时反射。正文只有 `.md` 这一份权威来源，不能继续在汇总 JSON 中保留可编辑副本。

已有纯文本便签同样拥有独立 `.md` 文件，但 `contentFormat` 保持 `PlainText`，应用内继续按纯文本解释，不能因迁移重新解释 `#`、星号和反引号。文件扩展名不会改变这一兼容规则。

### 3.2 视图状态与剪贴板

便签标题、正文、颜色、收藏、文档排序、附件和时间属于便签文件。快捷标签关闭历史、当前分类等属于宿主状态，继续保存在汇总 JSON；窗口大小、位置与置顶继续使用现有布局存储。

汇总 JSON 升级为新版本，增加独立便签存储版本标记；其 `Items` 只保留非便签记录，`RecentItems` 继续存放剪贴板历史。关闭标签不得删除 `.md` 或改写便签业务时间。正文自动保存不得为了同步更新时间而重写整个宿主状态文件。

### 3.3 附件

保留现有“托管副本”和“链接到原文件”两种语义。托管附件在便签元数据及正文中的本地引用尽量保存为相对于便签文件目录的路径，例如 `../attachments/<note-id>/image.png`；外部链接保留原有位置，不把链接模式偷偷转换成复制模式。

编辑器和预览必须接收便签所在目录作为解析基准。迁移只转换能够确认指向现有内部文件的引用，不用字符串替换去改写任意代码块、网络 URL 或用户链接。附件丢失时仍加载正文并显示缺失反馈。

新增附件先完成文件写入，再提交便签引用；移除附件先成功保存便签，再按现有规则清理不再引用的托管副本。失败时宁可留下未引用附件，也不能使已保存正文引用不存在的文件。本文只要求便签文档独立，带附件的文档整体迁移仍需携带相关附件。

## 4. 保存流程与连续编辑

正常编辑按以下顺序执行：原生编辑缓冲同步到会话，形成当前便签快照，编码并写入临时文件，提交正式文件，更新对应内存记录，最后发送包含便签 ID 的变更通知。

### 4.1 保存时机

| 场景 | 处理方式 |
| --- | --- |
| 连续输入后停顿 | 保留 600 毫秒防抖，合并这段输入后保存 |
| 长时间持续输入 | 从首次未保存修改开始计时，5 秒内发起一次保存；后续输入不重置该期限 |
| 切换便签、关闭窗口或正常退出 | 同步当前编辑缓冲，等待当前便签挂起及在途保存，确认成功后释放会话 |
| 保存期间继续输入 | 保留新修订，当前保存完成后合并补存最新快照 |
| 标题、颜色、收藏或附件变化 | 更新当前便签，避免重新扫描全部便签；保存成功前保留可恢复状态 |
| 关闭标签、移动窗口 | 只保存相应视图状态，不改写正文 |

5 秒是保存请求的最长期限，不是慢磁盘、错误或输入法组字状态下的完成时间保证。保存成功后仍有新修订时，从最早尚未保存的修改继续安排期限，不能让持续输入无限延后落盘。

输入法组字期间不能为了保存而强制结束组合或重绑正文。到期时保存当前已经提交到文档模型的文本；组字提交后立即按未保存状态继续调度。需要退出时先正常结束输入交接，再等待保存。

### 4.2 并发与线程

同一 ID 继续由 `NoteWorkspace` 共享一份 `NoteEditingSession`。同一便签一次最多一个在途保存，等待中的修改合并为最新状态，不为每次按键排队。不同便签可独立提交，集合级新增、删除和视图状态变更另行短暂互斥；不得用覆盖整段磁盘等待的全局锁阻塞其他便签的读取和输入。

快照在合适的 UI 线程交接点捕获，编码与文件提交不访问实时变化的集合或 UI 对象。耗时工作离开 UI 线程执行，不能认为使用 `await` 就能自动避免同步编码和文件替换造成的阻塞。完成结果回到 UI 后，仅在保存的修订仍是最新版本时清除未保存标记。

保留现有失败返回及草稿保留语义。失败不清除脏状态，不显示“已保存”，不无限立即重试；后续输入或用户重试可以再次发起保存。切换或关闭失败时按现有交互保留当前草稿与错误反馈，不静默销毁会话。

`MarkdownEditingSession` 同时服务其他 Markdown 场景。最长等待时间应作为可选能力接入，只在便签启用，避免无意改变待办备注的保存行为。原生编辑器自身的序列化防抖也必须在保存期限到达时同步，不能只保存会话里尚未更新的旧文本。

### 4.3 文件提交与恢复

沿用 `ResilientJsonStore` 已有的临时文件、替换、上一版备份、特定错误降级和错误传播原则。新增便签文件提交不应复制出另一套行为不同的可靠写入协议：若需抽取格式无关的文件提交函数，应限制在必要部分，并保留原 JSON 存储的现有回归覆盖。

每次写入使用同目录唯一临时文件。已有正式文件正常使用替换操作并保留 `.bak`；首次保存提交新文件。临时文件不进入便签枚举、搜索和备份。提交失败保持内存草稿与可恢复的正式版本，错误反馈包含当前便签而不暴露正文到日志。

不能笼统保证所有写入都原子：现有特定文件替换错误的降级路径不是原子替换。该路径仍须先写入并验证备份，再更新正式文件。应用启动时按单张便签恢复；不得因为一个文件损坏就把整个便签库当成空库。没有有效恢复来源时展示对应错误记录，避免用户误以为便签被删除。

“已保存”表示所选文件提交协议成功完成，不宣称能够承受任意硬件故障或断电。`.bak` 只提供上一版恢复，沿用现有备份保留政策，不扩展成新的历史版本系统。

## 5. 查询、通知和加载

`QuickCaptureService` 继续作为现有入口的协调服务，内部把便签写入路由到独立文件存储，把剪贴板和非便签写入路由到 JSON。便签查询及更新使用按 ID 建立的内存映射，不依靠反复遍历整个库定位当前便签。

变更通知至少区分单张内容修改、集合新增或删除、排序变化、宿主视图状态变化和剪贴板变化，并携带受影响的 ID。普通正文保存只更新当前便签及对应列表项；不再通知所有编辑会话去调用全量 `GetDataAsync`。列表首次加载、备份整体恢复等操作仍可执行一次全量刷新。

第一阶段启动时枚举并加载便签、建立内存映射，先复用当前列表需要正文摘要的模型；已加载便签不会因为每次编辑重新读目录。不为尚未证明必要的优化新增持久化索引。批量文件读取控制并发，避免同时启动数千个读取任务。

独立小文件会增加冷启动和首次全文检索的文件打开次数，这部分必须单独测量。如果真实数据证明不可接受，再增加可重建的摘要缓存和正文按需加载；缓存不能成为恢复便签的必需文件，也不能在每次正文保存时重写全库缓存。

## 6. 旧数据迁移与中断恢复

迁移在启动加载阶段完成，便签编辑和备份恢复在此期间不能并发写入。以新版本汇总 JSON 中的存储版本标记作为正式切换依据，不能仅凭 `notes` 目录存在就认定迁移成功。

1. 通过现有容错读取获得有效旧库。在任何改写前保存独立的迁移恢复副本，记录源版本与源文件指纹；不能只依赖下一次保存就会轮换的 `.bak`。
2. 按当前 `NoteWorkspace.IsNote` 规则划分有效便签，包含空白草稿、带图片附件的便签及旧纯文本便签。删除记录另行处理，不能因 `IsNote` 排除了已删除项而漏掉删除保护。
3. 在同级临时迁移目录生成每张便签文件与必要删除记录。保留业务 ID、正文、格式、时间、排序、收藏和附件；关闭历史仍保留在宿主状态。附件缺失只记录并呈现缺失，不阻塞正文保全。
4. 重新读取所有生成结果，对比 ID 集合、正文、业务字段及附件引用，核实源库没有变化。遇到重复 ID、非法路径、字段无法无损映射或任何写入失败时停止切换，保留恢复副本和诊断信息。
5. 将验证通过的目录发布为正式 `notes` 目录，再通过可靠文件提交写入新版本汇总 JSON：移除已迁出的便签正文，保留非便签记录、剪贴板与视图状态，同时写入存储版本标记。最后一步成功后，新格式成为唯一写入来源。
6. 重启重新加载新库确认数据一致。迁移恢复副本只按现有恢复策略或明确维护操作处理，本次迁移不自动删除它。

临时迁移目录附带小型进度说明，记录源指纹及已生成文件，支持同一来源的幂等重试。发布目录成功但最终标记写入失败时，旧格式仍是当前来源；下次只可在确认目录属于同次迁移且内容一致后继续，不能覆盖来源不明的现有便签目录。

切换标记已存在时，旧恢复副本绝不能再次作为普通输入导入，否则会复活已删除便签或覆盖新内容。自动迁移失败保持旧格式可读，不能一部分操作走新格式、一部分走旧格式。新格式不承诺旧版本应用可直接读取；需要降级时，通过迁移恢复副本或备份执行显式恢复，不能让旧版与新版轮流写同一数据目录。

### 删除与撤销

删除保护沿用现有按 ID 和更新时间合并的语义。为避免额外的“删除索引 + 文件移除”双文件事务，同一 `.md` 提交删除状态并清空标题、正文和内容引用，保留最小删除记录；正常枚举过滤这类记录。删除失败时便签仍然存在，不能先从 UI 永久移除。

撤销使用现有内存快照重新提交同一 ID 的有效便签。文件删除保护保留上限沿用现有 500 条规则，清理在维护路径中进行，不放到每次按键或正文保存路径。清理主删除记录及其恢复文件时必须遵守现有保留政策，防止遗留备份被误判为活跃便签。

## 7. 备份、恢复与存储目录兼容

当前 `CloudBackupDomains` 的便签数据范围只明确识别 `quick-capture/quick-capture.json`。独立文件上线时，必须同步更新云端与本地备份枚举、预览计数、校验、合并恢复及附件路径重定位，不能在正文已迁出后仍只备份汇总 JSON。

| 场景 | 必须满足的行为 |
| --- | --- |
| 新格式备份 | 包含有效便签文件与删除保护；排除临时文件、迁移工作目录和可重建缓存；附件沿用相应备份域开关 |
| 备份快照 | 先等待待保存便签，协调文件复制期间的短暂写入边界，避免同一便签正文与附件引用来自不同版本；网络上传不持有保存锁 |
| 旧版本备份恢复 | 在恢复暂存区先完成格式转换与验证，再进入正式应用阶段 |
| 新版本覆盖恢复 | 恢复与替换按现有范围语义执行；清除受影响内存缓存并通知相应会话重新加载 |
| 新版本合并恢复 | 按业务 ID、更新时间和现有删除冲突规则比较，不能仅按文件修改时间或文件名覆盖 |
| 恢复到新目录 | 修正托管附件解析基准；外部链接保持链接语义；缺失文件可见且不阻止正文恢复 |
| 托管数据目录迁移 | 把新便签目录纳入现有盘点、复制与完整性验证，保持数据根目录和恢复目录的现有行为 |

旧 `.bak` 及迁移恢复副本不能参与正常便签合并。备份和恢复保留现有范围选择，不因增加 Markdown 文件而顺便把外部链接文件或未启用的附件域上传。

## 8. 外部修改的最小支持

打开便签及应用重新激活时可检查文件是否改变；保存前比较上次读取版本，时间和长度可用于快速筛选，不能作为唯一冲突判定，应结合文件内容指纹。

内存没有未保存修改时可以重新读取；内存有草稿且磁盘也改变时保留双方内容，提示用户处理，不能自动用任意一方覆盖。外部文件丢失不能直接等同于应用内删除，更不能覆盖掉当前未保存草稿。

正常保留头部的外部编辑可以重新读取正文。头部缺失时以合法文件名中的 ID 定位，并在仍有内存记录时保留已有业务属性；冷启动无法恢复的属性使用默认值，保存时补回头部。头部损坏、版本不支持或头部 ID 与文件身份冲突时保留源文件并报告问题，不得自行重置为新便签。无头部正文不因为外观变化被误判为“损坏文件”并回滚。

第一阶段不增加常驻目录监听器。保存前检测只能降低外部覆盖风险，不能消除第三方编辑器恰好在检测后替换文件的竞态；本次不承诺跨进程同时编辑的一致性，也不引入协同算法。

## 10. 测试与验收

沿用现有 xUnit 项目及编辑会话测试，不新增测试框架。扩展 `NoteWorkspaceTests`、`MarkdownEditingSessionTests`、`QuickCaptureServiceTests`、`ResilientJsonStoreTests`、`WinStickerDataBackupServiceTests`、云备份范围测试，并为编解码和文件迁移添加必要的针对性用例。

### 10.1 数据与保存正确性

- 空白草稿、中文、表情、换行、代码块、正文开头的 HTML 注释、含 `-->` 的标题、未知元数据字段和旧纯文本内容均可往返；正文不被裁剪或重解释。
- 编辑一张便签只提交该文件与其恢复副本；其他便签及宿主 JSON 的字节和写入时间不变。验证实际提交调用，不能仅凭时间戳证明未发生写入。
- 持续输入超过 5 秒且没有 600 毫秒空闲时仍发起保存；输入法组字不被中断，提交后的内容不会漏存。
- 保存期间继续输入后最终保留最新文本；关闭及切换等待在途保存；相同 ID 的两个入口不相互覆盖。
- 磁盘拒绝写入、临时文件写入失败、替换失败后保留草稿并可重试，既不死锁也不无限循环。
- 单个文件不可读或损坏只影响对应便签；备份缺失、备份损坏及不支持的新格式都不导致整库清空。
- 删除、撤销、删除记录清理及备份合并不会复活内容，关闭标签不改变文档生命周期。

### 10.2 迁移与恢复

使用旧版混合数据覆盖普通便签、带附件便签、纯文本、空草稿、非便签、剪贴板、关闭历史、删除记录和缺失附件。验证迁移前后业务字段与正文一致；在生成文件、发布目录和提交切换标记等边界模拟中断，重启后不能出现重复导入、半切换和内容丢失。

验证旧、新备份的覆盖及合并恢复、不同备份域组合、恢复后重新启动、迁移到另一数据目录，以及相对图片引用在两个实际入口中的显示。附件域未启用时正文恢复成功，缺失附件有明确反馈。

### 10.3 性能验证

分别准备 100 张与 1,000 张便签，以每张约 4 KiB 正文作为常规数据，另测接近当前正文长度上限的长文；上限按字符数定义，不能把 256 KiB 文件大小等同于当前 256 × 1024 字符限制。用相同机器、目录和备份设置，对照修改前后的同一流程。

测试至少包含单张连续输入两分钟、频繁停顿、保存中继续输入、多入口打开及冷启动。记录实际文件提交次数和字节数、保存耗时中位数与第 95 百分位、输入与 UI 阻塞、全量查询调用次数，以及启动和首次全文搜索耗时。关闭其他入口与打开多个入口分别测量，确认不会随已打开会话数成倍复制全库数据。

验收首先满足可观测的结构要求：普通编辑不调用全库保存，不重新枚举目录，不触发全局列表重载；在内存已加载的情况下，保存一张便签的主体写入量由当前便签大小决定。性能结论必须附实际结果；如冷启动或搜索相对基线有明显退化，记录数据并在交付前确定是否需要缓存，不能只报告写入加速。
